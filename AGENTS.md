# AGENTS.md — read this first (Codex / any coding agent)

This repo is a Claude Code project that is now ALSO driven by Codex. Both agents share one working
tree, one set of rules, and one progress record. Nothing in this file replaces the rules below; it only
tells you where they are and in what order to load them.

## Load order (do this before touching anything)

1. `CLAUDE.md` — the project: graph model, data shape, fixed layer/domain slugs, workflow table, hard rules.
2. `docs/HANDOFF.md` — WHERE WE ARE: what is done, what is queued, what the user decided, what to do next.
   Updated at the end of every working session (by whichever agent worked). Append; never rewrite history.
3. `.claude/skills/enrich/SKILL.md` — the enrichment procedure (patch format, JOB 1–5, labels, build + verify).
   Its `references/*.md` hold the per-pipeline procedures (us / dart / intl / tw / edgar / conferences).
   `.claude/skills/chain-skeleton/SKILL.md` — how to build a new chain file. `ask-server` — the Ask tab engine.
4. `docs/memory/*.md` — a snapshot (2026-09-12) of Claude's persistent memory for this project: user
   preferences, decisions, rulings, gotchas, run histories. `MEMORY.md` there is the index. Read the index,
   then open only the files relevant to the task. Facts there were true when written; verify paths/flags.

When a user command matches the trigger table in `CLAUDE.md` ("enrich us", "enrich edgar", "build chain
skeleton for X", "Transcript:<company>", ...), follow the matching skill file verbatim. Do not improvise.

## Non-negotiable rules (short form — details in CLAUDE.md and the skills)

- ADD only. Never drop or overwrite nodes, edges, quarterly_data or contracts. The user owns the structure.
- Enrichment writes `patches/<company>_<quarter>.json`, NEVER `chains/` directly. `apply_patches.py`
  (run by `graph_build.py --sync`) is the only writer of `chains/` during enrichment.
- Every figure must come from a transcript/filing saved under `transcripts/`. No news, no model knowledge,
  no web facts. The user fully reverted a news/knowledge-edge program once; do not re-propose it.
- Litmus test before adding a company: does its stock directly benefit from the product being built?
- Company names must be byte-identical across chain files (see `docs/memory/naming_rules.md`).
- Tag every new entry (`topics`, and `slot` / `capex` where relevant) — the web tabs are derived from tags.
- NEVER `git commit` or `git push` unless the user says so in that turn ("커밋해" / "푸시해" / commit / push).
  Ending a report with the ready-to-paste commit command is fine and welcome.
- Never hand-edit anything under `graph/` or `web/public/data/` — they are generated by `graph_build.py --sync`.
- All user-facing web-app text is English. The user chats in Korean; answer in Korean, short and casual.
- New Python is explicit and commented in English (the user is learning Python through this project).
- Do not build future phases (scheduler, new pipelines) unless asked.
- NEVER run `node local-ask/up.mjs` or `down.mjs`. The live Ask tab reaches this PC through a fixed Tailscale
  Funnel address already set on Vercel; `up.mjs` would overwrite it with a throwaway Cloudflare address.
  "ask 실행" = the `ask-server` skill (health checks only). The website has no API fallback (no Gemini, no
  Anthropic API) — Claude answers come only from this PC.

## Recording your progress (MANDATORY — Claude and Codex read each other's notes here)

The user switches between Claude Code and Codex. Neither agent can see the other's chat, so the ONLY
way the next agent knows what you did is what you write in `docs/HANDOFF.md`. Before you end a session
(or when the user says "record", "기록해", "정리해", or switches agents), do ALL of this:

1. **Append one entry to `docs/HANDOFF.md` → "7. Session log"** (never edit older entries). Template:
   ```
   - **YYYY-MM-DD (Codex)** — <what was asked>. Done: <files/patches written, counts, build + verify result
     (N pass / N fail)>. Decisions: <anything the user decided or rejected — quote the Korean if short>.
     Left open: <what is unfinished, exact resume point: file, queue, batch, command>. Uncommitted: yes/no.
   ```
2. **Edit in place** `docs/HANDOFF.md` §3 "Current state" (graph counts, git state, queue sizes) and
   §4 "Next up" (remove what you finished, add what is now next, keep the order meaningful).
3. **If a rule, preference or ruling changed** (the user corrected you, rejected an idea, chose a source,
   renamed something), also write it into the matching file in `docs/memory/` (or a new short file there,
   same frontmatter shape, plus one index line in `docs/memory/MEMORY.md`). Claude re-imports that folder.
4. **If you touched pipeline queues or state files** (`*/pending.json`, `*/sync_state.json`,
   `edgar/STATUS.md`, `enrich_log.json`), say which, so the next agent does not re-run a done step.
5. **Never leave a half-applied step unrecorded.** If you were cut off mid-run, the first thing the next
   session must be able to read is "batches 1–4 have patches, 5–8 do not."

Claude follows the same rules and writes "(Claude)" in its entries. Read the newest log entries at the
start of EVERY session before doing anything — the other agent may have worked since you last did.

## Standard end-of-work sequence

1. `python graph_build.py --sync`  (applies patches → merged graph → derived views → web/public sync;
   also runs `verify_graph.py` on the labels just applied — read every `[fail]` / `[warn]` line).
2. Fix the patch and rebuild until 0 fail.
3. Mark the pipeline queue done (`av.py done`, `investing.py done --kind conference`, `edgar_pull.py done`, ...).
4. Record progress as described above (session log entry + §3/§4 refresh + docs/memory if a rule changed).
5. Report to the user with the commit command; do not run it.
